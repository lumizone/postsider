# Phase 5 controller rulings on open product questions (2026-11-05)

Binding for the spec and plan. Where a question had a conservative and a convenient answer, the conservative one was chosen. An implementer who disagrees reports it; they do not deviate.

Q1. Email approver links: default off or on? RULING: off. Enabled only with `APPROVAL_EMAIL_LINKS=true`. With it unset, `notifyApprovers` sends exactly today's plain email. Reason: links are bearer credentials that also pass through Temporal workflow history; the owner opts in knowingly. TTL `APPROVAL_LINK_TTL_HOURS`, default 48, clamped to 1..168.
Q2. Must an email link require login? RULING: no (that is the point of one click), but the decision is attributed to the member the email was sent to, re-checks membership, role and stage eligibility at decision time, is single use, and needs the two step challenge. A forwarded email is the accepted residual risk and is documented. A login-required variant is a later option, not Phase 5.
Q3. Self-approval. RULING: automation never decides what it created or requested (always on, no flag). For humans it is controlled by the flow flag `preventSelfApproval` (default true for flows created in Phase 5); the implicit single stage (no flow) keeps today's behaviour so a solo owner can approve their own post. `requireDistinctApprovers` (default true) stops one actor deciding two stages of the same approval. Both are skipped for guests (a guest is not a member).
Q4. Which role can decide a stage? RULING: `minRole` is ADMIN or SUPERADMIN only; USER can never decide. `approverUserIds` narrows to named members. Roles stay `Role`, no custom roles.
Q5. SUPERADMIN and the approver list. RULING: a SUPERADMIN bypasses `approverUserIds` (break-glass, avoids deadlock when listed members leave) but never bypasses self-approval or distinct-approver rules. If that deadlocks a solo owner, they set the flag off on the flow.
Q6. Stage progress webhooks. RULING: no new event name (the four are frozen). `approval.requested` and `approval.resolved` payloads gain `approval.stage`. `approval.resolved` is emitted once, when the approval becomes final (APPROVED after the last stage, REJECTED at any stage). Polling `GET /approvals` shows stage progress in between.
Q7. Slack: webhook notify only, or interactive buttons? RULING: notify only, through the existing webhook subscription outbox (Slack incoming webhook URL detected by host `hooks.slack.com`). No Slack app, no new env, no stored tokens. The message has no post content or identifiers and links to login-gated pages. Interactive approve is deferred (identity mapping and secret storage are product decisions).
Q8. Which scopes manage approval flows through the public API? RULING: `policies:read` and `policies:write` (never granted by default). Who approves is governance, same blast radius as rules. The dashboard routes are admin only. `approvals:decide` only deciding; it cannot edit flows.
Q9. Workspace provisioning. RULING: customers only (list, create, rename, archive, assign channel by id), admin caller, 200 customer cap, archive detaches channels and keeps posts. Out: creating organizations, inviting members, connecting channels without a human OAuth step. No MCP tool for provisioning. Open question left to the owner: whether agencies need tenant (organization) creation through the API, which touches billing seats and isolation.
Q10. Make and Zapier. RULING: documentation for Make, a Zapier CLI scaffold plus pure mapping modules with node:test specs, nothing submitted, `zapier validate` is an owner action. Polling uses `GET /approvals`. No new webhook event, no new auth type.
Q11. i18n scope. RULING: new namespaces `approverLink` and `approvalFlows` and the few new `approval.*` stage keys go into `en.ts` and `pl.ts` only; the other nine locales fall back to English (same as Phase 4 for new namespaces). A parity spec checks en/pl and placeholders and bans U+2013/U+2014.
Q12. MCP deciding. RULING: one tool `postsider_decide_approval`, stdio only, registered only with `POSTSIDER_MCP_ALLOW_APPROVAL_DECISIONS=true`, never on the hosted OAuth server (hosted tokens cannot hold `approvals:decide`). Hosted stays 40 tools; stdio 41 by default, 42 with both opt-ins. No MCP list-approvals tool (REST and n8n cover polling). Package versions are not bumped (owner release step).
Q13. `guestToken` storage. RULING: hash at rest (SHA-256 hex in `guestTokenHash`), backfill from plaintext in the migration, then set plaintext `guestToken` to NULL; column kept one release. The dashboard never returns token material; admins get `hasGuestLink` and `guestLinkExpiresAt`.
Q14. Guest links and stages. RULING: a guest link can resolve a stage only when that stage has `allowGuest` true (default false for flow stages, true for the implicit stage). `createGuestLink` refuses otherwise (400 `guest_not_allowed_for_stage`). This closes the "admin mints a link to approve their own post" path for flows that forbid self-approval.
Q15. Approval expiry and reminders. RULING: not in Phase 5 (orchestrator cron plus product decision). Only link tokens expire. Listed in the spec as dropped.
Q16. Key limits and approving. RULING: approving schedules the post, so a key needs the `SCHEDULE` action on the post's channel under its Phase 3 limits to decide. A Draft-only key cannot approve. A reject schedules nothing, so it is not gated by the key limits (review fix).
Q17. Idempotency for deciding. RULING: optional `Idempotency-Key` through `PublicApiIdempotencyService`; without it, same decision repeated returns 200 `changed: false`, opposite decision 409 `approval_already_resolved`.
Q18. Audit. RULING: no new audit event type. `post.approval_resolved` metadata gains `via`, `stage`, `stageCount`, `final`; those keys are added to the timeline allow-list. Customer provisioning is not audited in Phase 5 (no event type fits; revisit when audit gets a non-post target).
Q19. Cross-repository work. RULING: the n8n package lives in its own git repository; its task commits there on branch `feat/approvals-policies-groups` and never pushes or publishes. The monorepo plan only records its contract (spec R7). Zapier assets live in this repository under `examples/automation/zapier/`.
Q20. Parallel execution. RULING: the plan's dependency table is authoritative. Tasks tagged INDEPENDENT may run in parallel Sonnet implementers if they touch disjoint files; `database.module.ts`, `public.api.module.ts`, `api.module.ts` and the locale files `en.ts` and `pl.ts` are shared append-only files: each task appends its own lines, and the controller resolves trivial merge conflicts, then re-runs the owning task's tests.
