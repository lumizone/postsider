# Control Plane Phase 4: Agent Control Center (Agent activity UI)

Date: 2026-11-04
Branch: `feat/control-plane-p4-agent-center` (stacked on `feat/control-plane-p3-policy` at aca5fae, which is stacked on Phase 2 and Phase 1)
Plan: `docs/superpowers/plans/2026-11-04-control-plane-phase4-agent-control-center.md`

## 1. Problem

Phases 1 to 3 made automation reliable, attributable and governable, but all of it is only visible through the public API and MCP. An owner who lets agents, n8n flows and MCP clients create posts has no place in the dashboard to answer: what did the agents do today, what is waiting for me, what was blocked by a policy, what failed and can it be retried safely, who exactly did this. Policies and per-key limits can only be managed with API calls, and a policy that lists the `USER` actor is never checked when a person saves a post in the dashboard.

## 2. Goals and non-goals

Goals: a dashboard page "Agent activity" (inbox plus summary), a detail drawer with verified actor, claimed provenance, approval, policy outcome, per-destination results, previews and an audit timeline; approve, reject, bulk approve/reject and safe retry from that page; a Settings page for policy rules with a dry run; per-key action and channel limits in the API key dialogs; dashboard write-time evaluation of rules that list the `USER` actor.

Non-goals (binding, decisions D7): no change to publishing internals, workflow files (`post.workflow.v1.0.*.ts`) or `publicApiRetentionWorkflow`; no change to public API contracts, scopes, MCP tools or webhooks; no billing change; no new MCP tool. The frontend never calls `/public/v1` (it uses the session-authenticated dashboard API). Not in this phase: realtime push or polling timers, saved views, exports, editing a post inside the drawer, AI judgement.

Phase 1 `PostsService.retryFailedByGroup(orgId, group, { includeUnknownOutcome })` returns `{ group, results: [{ postId, integrationId, previousState, action, reason? }] }` and exists only behind the public route; there is no dashboard route. Phase 3 changes its options (`routeToApproval`) and adds `PostPolicyGateService.gateRetry`; the dashboard route must run the same sequence as the Phase 3 public handler.
9. Phase 2 data available per row: `createdBy*` and `lastModifiedBy*` (type plus user, api key or oauth client id, no foreign keys), five claimed provenance columns, `PostApproval` with `requestedBy*`, `decidedByType`, `approverId`, `guestName`, `guestEmail`, and audit events through `AuditEventsService.list(orgId, { targetType, targetIds, limit, cursor })` (resource rows only). Phase 3 adds `post.policy_evaluated` events whose metadata is primitives only (`effect, phase, matchedCount, ruleIds` as the first 5 ids joined by `,`, `ruleNames` joined by ` | ` cut at 200).
10. CORRECTION (lastModifiedBy after publish): the publisher writes `lastModifiedByType = SYSTEM` on success (Phase 2 R1.3), and a human who approves overwrites it too. So `createdBy` is the reliable automation marker for published posts and "touched by automation" means created by automation OR currently last modified by automation.
11. CORRECTION (time): there is no `publishedAt` column and `User.timezone` is an `Int` offset. `Organization.defaultTimezone String?` exists but is documented as the queue-schedule pre-fill. "Today" is therefore computed in: the browser IANA zone sent by the page, else the organization default, else UTC. "Published today" uses `Post.updatedAt` of PUBLISHED rows as the proxy (the publisher is the last writer of a published row; no new column, D7).
12. CORRECTION (reschedule): the calendar drag and drop calls `PUT /posts/:id/date` with `action: 'schedule'` (not `'update'`). Phase 3 `gateStatus(orgId, postId, 'schedule')` evaluates the STORED publish date, which is wrong for a window or daily cap rule when the date is the thing being changed. Phase 4 adds one gate method that evaluates the new date (R5).
13. The dashboard composer sends `type: 'schedule' | 'draft' | 'now' | 'update'`; `'update'` is a real `CreatePostDto.type` (edit in place). Phase 3's evaluation types are `draft | schedule | now`, so `'update'` must be mapped (R5).
14. `Post` indexes are single column (`state`, `organizationId`, `updatedAt`, ...). There is no composite index for "org + state + updatedAt". Prisma migrations here have no `CONCURRENTLY` precedent.
15. OAuth client display names come from public dynamic client registration (`McpOAuthClient.name`), so they are untrusted text. `ApiKey` rows are soft deleted (names stay resolvable); `OAuthApp` is organization scoped; `McpOAuthClient` is global.
16. Calendar deep links: the only existing query contract is `?connect=1` (consumed in `components/calendar.tsx`, then stripped with `history.replaceState`). Opening a post for edit is `openEventForEdit(ev)`, which needs only `ev.id` (others are fallbacks).

## 4. Requirements

Numbering groups the decisions D1 to D7. All are binding.

### R1 Read API: list, summary, filters (D1, D4)

New session-authenticated controller `AgentActivityController` at `/agent-activity`, registered in `authenticatedController`. Any org member can read. Everything is scoped by `org.id`.

Row bucket (single source of truth, a pure function `bucketOfRow({ state, errorCategory, errorRetryable })`):

| Row | Bucket |
|---|---|
| `QUEUE` | `scheduled` |
| `DRAFT` | `draft` |
| `HELD` | `held` |
| `PUBLISHED` | `published` |
| `APPROVAL` | `review` |
| `ERROR` and `errorCategory = POLICY_BLOCKED` | `blocked` |
| `ERROR` and `errorCategory = UNKNOWN_OUTCOME` | `unknown_outcome` |
| `ERROR` and `errorRetryable = true` (any other category) | `retryable` |
| any other `ERROR` (including legacy rows with null category) | `failed_other` |

Group bucket is the highest priority row bucket: `unknown_outcome > blocked > retryable > failed_other > review > held > scheduled > draft > published`.

R1.1 `GET /agent-activity/summary?timezone=<IANA>` returns `{ timezone, dayStart, dayEnd, actionsToday, waitingForReview, policyBlocked, failed: { total, retryable, unknownOutcome, other }, publishedToday }`. Counting unit is the destination (top-level row with `parentPostId = null`, `deletedAt = null`, integration not deleted), because an approval and a retry act per destination. `actionsToday` = resource audit events of the organization created inside today's bounds whose `actorType` is `API_KEY` or `OAUTH_CLIENT`. `waitingForReview`, `policyBlocked` and `failed.*` are the open backlog now (not limited to today: an unresolved item from yesterday still needs a decision), computed from one `groupBy` on `(state, errorCategory, errorRetryable)` for `state in (APPROVAL, ERROR)` reduced through `bucketOfRow`. `publishedToday` = PUBLISHED destinations with `updatedAt` inside today's bounds that automation created. Timezone: valid IANA query value, else `org.defaultTimezone`, else `UTC`; an invalid value never errors. `dayStart`/`dayEnd` are the UTC instants of local midnight to next local midnight (a DST day is 23 or 25 hours long).
R1.2 `GET /agent-activity` list of post groups. Query (all optional): `bucket` (one of `all attention review blocked failed retryable unknown_outcome failed_other published scheduled draft held`, default `attention`; `attention` = review, blocked, and every failed bucket; `failed` = retryable, unknown_outcome and failed_other), `scope` (`relevant` default or `automation`), `integrationIds` (comma separated, at most 20), `actor` (`USER:<id>`, `API_KEY:<id>`, `API_KEY:legacy`, `OAUTH_CLIENT:<id>`, `SYSTEM`), `agentName`, `source` (exact match on the claimed columns, at most 255 characters), `from`, `to` (ISO 8601, `from <= to`, applied to `updatedAt`), `limit` (1 to 50, default 25), `cursor`. Scope `automation` = `createdByType in (API_KEY, OAUTH_CLIENT)` OR `lastModifiedByType in (API_KEY, OAUTH_CLIENT)`; `relevant` = automation OR `state in (APPROVAL, ERROR)` (anything needing attention regardless of who created it). `actor` matches createdBy OR lastModifiedBy. A group matches when at least one of its destinations matches; the response then carries ALL top-level destinations of that group. Order: group `max(updatedAt)` of the matching rows descending, then `group` descending. Cursor is opaque `{ t: ISO, g: group }`, a tampered cursor is 400. Response `{ groups: GroupSummary[], nextCursor: string | null }`.
`GroupSummary` = `{ group, updatedAt, bucket, contentPreview (plain text, at most 240 characters), destinations: [{ postId, integrationId, integrationName, providerIdentifier, picture, state, bucket, errorCategory, errorRetryable, publishAttempts, releaseURL, publishDate }], createdBy: ActorDisplay | null, lastModifiedBy: ActorDisplay | null, claimed: { agentName, workflowId, runId, externalRef, source } (nulls kept), pendingApprovalIds: string[], canRetry: boolean }`. `canRetry` is true when a destination bucket is `retryable`, `unknown_outcome` or `failed_other` and its `releaseId` is null or `'missing'` (Phase 1 skips rows that already have a real release id).
R1.3 `GET /agent-activity/filters` returns the options the page needs that the channel list does not already give: `{ actors: [{ key, type, id, name, state }], agentNames: [{ value, label }], sources: [{ value, label }] }` (`value` is the stored text used for exact-match filtering, `label` is the cleaned text for display) over the last 90 days of top-level rows, at most 50 each, ordered by most recent use. Actors are distinct createdBy or lastModifiedBy automation identities (`API_KEY`, `OAUTH_CLIENT`), names resolved by R4.
R1.4 Query efficiency: no N+1 (rows for a page are one `findMany` by group list, names resolved in at most four batched queries: users, api keys, mcp oauth clients, oauth apps). One additive migration adds `@@index([organizationId, state, updatedAt])` to `Post`. The executor proves with `EXPLAIN` on seeded throwaway data that summary and list queries use it and records the result; the index is created with `CREATE INDEX CONCURRENTLY IF NOT EXISTS` in a single statement migration, with a documented fallback to a plain `CREATE INDEX` if Prisma refuses (it runs the file in a transaction).

### R2 Detail API (D2)

`GET /agent-activity/groups/:group` (404 `Group not found` for unknown or foreign groups, same response) returns:
`{ group, updatedAt, destinations: [Destination], policy: { recorded, current }, timeline: [TimelineItem] }`.
`Destination` = `{ postId, integration: { id, name, providerIdentifier, picture }, state, bucket, errorCategory, errorRetryable, errorMessage (stored error text, at most 500 characters), publishAttempts, lastPublishAttemptAt, releaseURL, publishDate, contentText (plain text of the full content), image (the raw JSON string of the media column, parsed by the existing `parsePostMedia` on the client), thread: string[] (child rows ordered by creation, plain text), firstComment: string | null, createdBy, lastModifiedBy, claimed, approval }`.
`approval` = `null` or `{ id, status, note, requestedAt, resolvedAt, requestedBy: ActorDisplay | null, decidedBy: ActorDisplay | { type: 'GUEST', name, email } | null }`. Built from an explicit `select` that never includes `guestToken` or `guestTokenExpiresAt` (a test asserts the response has no such key anywhere).
`policy.recorded` = the newest `post.policy_evaluated` event of the group rows (`{ effect, phase, at, ruleNames: string[], matchedCount }`) or `null`. `policy.current` = a live re-evaluation of the stored destinations against the current rules (Phase 3 `PolicyEvaluationService`, action SCHEDULE, `approved` true when the approval is APPROVED), `{ effect, matched: [{ ruleId, name, effect, condition }] }`, or `null` when the service is absent, nothing is evaluable (all PUBLISHED) or the evaluation throws (logged, never fails the detail).
`timeline` = `AuditEventsService.list` for all row ids of the group including soft deleted ones (`PostsRepository.getPostIdsInGroupIncludingDeleted` of any row), newest first, at most 100, each `{ id, type, createdAt, postId, actor: ActorDisplay | { type: 'GUEST' }, metadata }`.
`ActorDisplay` = `{ type: 'USER' | 'API_KEY' | 'OAUTH_CLIENT' | 'SYSTEM', id: string | null, name: string | null, state: 'ok' | 'revoked' | 'unknown' | 'legacy', authorizedBy: string | null }`. Claimed provenance is returned under `claimed` and the UI labels it "claimed by the client, not verified".

### R3 Actions (D3)

R3.1 Approve and reject single items use the existing `PUT /approval/:id/approve|reject` (no new code). The UI shows the buttons only for ADMIN and SUPERADMIN.
R3.2 `POST /agent-activity/approvals/bulk` (admin only through `@CheckPolicies([Create, Sections.ADMIN])` and `assertCanApprove`, checked before anything is touched). Body `{ action: 'approve' | 'reject', approvalIds: string[] (1 to 50, distinct), note?: string (at most 500) }`. Sequential per item; one failure never stops the rest. Response `{ results: [{ approvalId, postId: string | null, status: 'done' | 'skipped' | 'failed', reason?: 'already_resolved' | 'not_found' | 'error', message?: string }], summary: { done, skipped, failed } }`. Idempotent: an already resolved approval is `skipped` (`already_resolved`), another organization's id is `skipped` (`not_found`), a second identical call changes nothing.
R3.3 `POST /agent-activity/groups/:group/retry-failed` (admin only) body `{ includeUnknownOutcome?: boolean }` (default false). Runs the same collaborators in the same order as the Phase 3 public `retry-failed` handler (write-time `gateRetry`, then `retryFailedByGroup`) and returns its result plus the policy outcome. `unknown_outcome` rows are re-armed only with `includeUnknownOutcome: true`. A 422 `policy_blocked` body is passed through unchanged. 404 for an unknown group.
R3.4 UI rule for `unknown_outcome`: the retry button opens a confirm dialog "The platform did not confirm whether this was published. Check the channel first. A retry may post a duplicate." with a required checkbox "I checked the platform" that enables the confirm button; only then the request carries `includeUnknownOutcome: true`. Bulk retry is not offered. A group with both kinds shows two controls: "Retry failed" (always sends `includeUnknownOutcome: false`, so the server skips the unknown_outcome rows) and "Retry anyway" (the dialog).
R3.5 Open in editor and calendar are links. `Calendar` gains two query consumers (same pattern as `connect=1`): `?post=<postId>` opens that post in the existing edit modal, `?date=YYYY-MM-DD` moves the visible month and selects the day. Both parameters are validated by a pure parser and stripped after use. Published rows link to their `releaseURL` (opened with `rel="noopener noreferrer"`) instead of the editor.

### R4 Actor display names (D2, D4)

`ActorDirectoryService.resolve(orgId, refs)` batches: users that belong to the organization (`UserOrganization`), API keys of the organization (selecting only `id, name, deletedAt`, never `key`), `McpOAuthClient` by id, `OAuthApp` by id and organization. `state` is `revoked` for a soft deleted key, `unknown` when no row is found (or a user who left the organization), `legacy` for `API_KEY` with a null id. Display names are cleaned (control characters removed, trimmed, at most 80 characters). An `OAUTH_CLIENT` actor carrying a user id also gets `authorizedBy` (that user's name). `SYSTEM` and `legacy` have `name: null` and the client localizes them. No secret, token or email beyond what the approval page already shows to members is returned (users show `name`, else the email, as `approval-api` does today).

### R5 Dashboard write-time policy evaluation for USER rules (D6)

Phase 3 deferred it (its fact 12). Phase 4 wires the dashboard to the same gate service the public API uses. Semantics are identical to the public API: BLOCK -> HTTP 422 `{ error: 'policy_blocked', msg, policy }`, nothing written; REQUIRE_APPROVAL -> the post is saved as a DRAFT and an approval is requested (`approvalRequested: true`); drafts are reported, not enforced (Phase 3 R4.0); the publish-time guard stays the backstop.
R5.1 `PostsController.createPost` (`POST /posts`, create and edit): map the dashboard type with a pure `dashboardPolicyType('draft' | 'schedule' | 'now' | 'update')` (`update` -> `schedule`), call `preflightWrite(orgId, body, actorFromUser(user))` before `createPost`, pass `forceDraftIntegrationIds`, then `finishCreate`. The response stays the existing array; each element gains `policy` and `approvalRequested` (additive). Evaluation failures bubble as 500, never as ALLOW.
R5.2 `PostsController.changeDate` (`PUT /posts/:id/date`): when `action === 'schedule'` call the new `PostPolicyGateService.gateReschedule(orgId, postId, date, actor)` BEFORE `changeDate`. It evaluates the stored post as a `SCHEDULE` target with `scheduledAt` set to the NEW date (`approved` from the post's approval), BLOCK throws `PolicyBlockedException`, REQUIRE_APPROVAL routes the post to approval (workflow terminated, date not applied) and returns `{ proceed: false, policy }`; the controller then answers `{ approvalRequested: true, policy }` without calling `changeDate`. `action === 'update'` is not gated (pure date shift of the same state; the publish-time guard re-checks windows and caps).
R5.3 Not gated in this phase (documented residuals): CSV import, duplicate (always a draft), evergreen recycling, and `ApprovalService.scheduleApprovedPost`. They remain covered at publish time.
R5.4 Frontend feedback (Task 15): a 422 `policy_blocked` shows "Blocked by policy: <rule names>" in the composer error banner and in the calendar reschedule error; a response with `approvalRequested` shows a dismissable notice "Sent for approval instead of being scheduled" with a link to /approval. The pure formatter lives in `lib/policy-errors.ts`.

### R6 Policy management: dashboard API and UI (D5)

R6.1 `PoliciesController` at `/policies` in `authenticatedController`, all routes admin only: `GET /policies`, `POST /policies`, `PUT /policies/:id`, `DELETE /policies/:id` (delegating to Phase 3 `PolicyRulesService` list/create/update/remove/toPublicRule with Phase 3 DTOs and limits; 404 for foreign ids), and `POST /policies/evaluate` (dry run). Rule changes write the same security audit entries as the public controller (`policy.create|update|delete`, input = rule id and name only, never words). The dry run body is the Phase 3 `EvaluatePolicyDto` plus optional `asActor: { type: 'USER' | 'API_KEY' | 'OAUTH_CLIENT' | 'SYSTEM', apiKeyId?: string }` (default: the signed in user, which only matches rules that list `USER`); an `apiKeyId` must belong to the organization (400 otherwise); for `API_KEY` with an id the key's own limits are also checked with Phase 3 `checkKeyPermission` and returned as `key`. Response shape equals the public dry run: `{ effect, matched, channels, key }`. Nothing is written by a dry run.
R6.2 Page `/settings/policies` (nav item under Settings, minRole ADMIN): list rules ordered by priority with a monochrome effect chip, an on/off switch (`Switch` from settings-ui, optimistic with rollback), edit and delete (ConfirmDialog); a rule form in a modal (name, effect, condition with its parameter editor, priority, filters: actor types, API keys, channels, providers); client validation mirrors the server limits in a pure `policies-model.ts` (name 1 to 120, priority 0 to 1000, words 1 to 100 entries of 1 to 100 characters distinct case-insensitively, window days 1 to 7 of 0..6 with `start !== end` in `HH:MM`, IANA timezone, daily cap 1..10000, filter arrays at most 100); the server stays authoritative and its 400/422 messages are shown. The limits (50 enabled, 200 total) surface as the server error `policy_limit_reached`. A "Test a post" panel runs the dry run with channel picker, type (draft, schedule, now), optional date, text, media toggle (image or video), "As" selector (me, an API key, any OAuth client, system) and shows effect, matched rules, per-channel effects and the key check.
R6.3 API key dialogs (`app/settings/api/page.tsx`): the create form and the edit modal get a "Permissions" section: a switch "Limit what this key can do" revealing action checkboxes (Draft, Schedule, Publish now) and a channel multi-select (from `getIntegrationChannels`); switch off sends `allowedActions: []` and `allowedIntegrationIds: []` (unrestricted, so a clear is explicit); with the switch on and nothing selected in both lists the Save/Create button is disabled with a hint (it would mean unrestricted); list rows show a summary ("All actions, all channels" or "Draft only, 2 channels"). A pure `key-permissions-model.ts` builds payloads and summaries. No new backend endpoint: Phase 3 already extends the settings API (the executor re-checks Preconditions). Legacy organization keys and OAuth tokens are not restricted by this feature and the dialog says so in one line.

## 5. Compatibility and rollout

- One additive migration (an index on `Post`). No data rewrite. Deploy order: migration, then backend, then frontend. A new frontend against an old backend shows the new pages' error banner (404 on `/agent-activity`); an old frontend against a new backend is unaffected.
- Behavior changes to announce: dashboard `POST /posts` and `PUT /posts/:id/date` may answer 422 `policy_blocked` or return `approvalRequested` once an organization has rules that list `USER`; their array and object shapes only gain keys. Organizations without rules see no change.
- The Agent activity page is read-only for members with role USER.

## 6. Risks and known residual issues

- Group ids change on edit (fact 6): a drawer open while an agent edits the post answers 404. Handled in the UI; the list refetch shows the new group.
- Attention tiles are open backlog, so an old unresolved ERROR row keeps counting until it is retried, edited or deleted. There is no "dismiss" in this phase (open question 1).
- "Published today" and the `updatedAt` date filter are proxies (fact 11); anything that rewrites a PUBLISHED row's `updatedAt` shifts it.
- Human edits overwrite `lastModifiedBy`, so a post an agent created and a person later edited is still found through `createdBy`, but a post a person created and an agent edited stops matching "automation" once the publisher or an approver writes SYSTEM or USER (fact 10).
- Counts are per destination while the list is per group; a three channel post waiting for review counts 3 and shows once.
- Dry run "As an API key" evaluates limits and rules but cannot know the key's real actor id for legacy org keys (`API_KEY:legacy`).
- Bulk and retry are admin only in the dashboard even though the public API lets any `posts:write` key retry; this is deliberate (open question 4).
- Mocked Playwright checks prove layout and wiring, not real backend behavior; backend behavior is covered by the HTTP specs and a manual run in the final task.

## 7. Open questions

1. Should open attention tiles (review, blocked, failed) be limited to items touched today or in the last N days, as the decision text for the summary bar suggests? This plan counts the open backlog and limits only "Actions" and "Published" to today.
2. Is `Post.updatedAt` acceptable as the "published today" proxy, or should a later phase add `publishedAt` (needs a publisher change, forbidden here)?
3. Is a single statement `CREATE INDEX CONCURRENTLY` migration acceptable for the large `Post` table, given Prisma runs migration files in a transaction (fallback documented)?
4. Retry and bulk approve are admin only in the dashboard. Should plain members (role USER) be allowed to retry their own failed posts?
5. Gate dashboard drag reschedule against the NEW date (new `gateReschedule`) as specified, or leave reschedules to the publish-time guard?
6. Default list scope `relevant` includes human posts that are in APPROVAL or ERROR. Prefer automation-only by default with the checkbox off?
7. Policy rules can contain banned word lists; the page is admin only. Should members with `posts:read`-equivalent be able to see rule names (the 422 already shows them)?
8. New namespaces are translated only in English and Polish; other locales fall back. Acceptable?
9. Playwright is not a declared dependency. Add it as a root devDependency, or keep the ad hoc script that skips when it is missing?
10. Timeline shows the latest 100 events per group. Enough, or add "Load older"?
