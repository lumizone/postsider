# Control Plane Phase 3: Policy engine v1

Date: 2026-11-04
Branch: `feat/control-plane-p3-policy` (stacked on `feat/control-plane-p2-identity` at 4a105d7, which is stacked on Phase 1, PR #43)
Plan: `docs/superpowers/plans/2026-11-04-control-plane-phase3-policy-engine.md`

## 1. Problem

Phase 1 made publishing reliable and Phase 2 made every write attributable. Nothing yet lets an owner limit what an automation may do:

- `posts:write` allows drafts, real scheduling and immediate publishing alike (`docs/API-MCP-TRUST.md` says so). A key cannot be "draft only" or "this channel only".
- The approval flow exists but is opt-in per post: an agent decides whether to ask. An owner cannot say "anything an agent posts with a link needs a human".
- There is no organization-wide guard (banned words, posting windows, daily caps) that holds even when the agent, the n8n flow or a later edit tries to get around it.

## 2. Goals and non-goals

Goals: per-key action and channel limits; organization policy rules that can force approval or block; one pure evaluator used at write time and again at publish time; every non-ALLOW outcome recorded and visible in API responses; a scoped management API, a dry run and one MCP tool.

Non-goals (binding): no frontend (the Agent Inbox and any policy UI are Phase 4), no billing change, no change to MCP OAuth flows, no edit of any `post.workflow.v1.0.*.ts` file or of `publicApiRetentionWorkflow`, no AI-based content judgement, no per-user dashboard rules UI, no rule templates. Dashboard create/edit calls are not evaluated at write time (section 3 fact 12); they are still caught at publish time.

## 3. Verified facts about the code (this worktree)

CORRECTION marks where the decisions assumed something that is not so.

1. `ApiKey` (`schema.prisma` ~1075) has `scopes String[]` and no per-action or per-channel columns. `PublicAuthMiddleware` sets `req.publicApiCredential = { type, id? }` and runs `next()` inside `runWithActor(actorFromPublicCredential(...))`. `OrganizationRepository.resolvePublicApiCredential` reads the row on every request (`select: { id, scopes, organization }`), so a permission change is effective on the next request with no cache. Legacy organization keys (`type: 'legacy'`) have no row; MCP/OAuth tokens have no `ApiKey`. Therefore D1 limits apply to `api-key` credentials only and nothing else is restricted.
2. API key CRUD lives in `settings.controller.ts` (`GET/POST /settings/api-keys`, `PUT /settings/api-keys/:id`) over `CreateApiKeyDto` / `UpdateApiKeyDto extends PartialType(...)` and `OrganizationRepository.listApiKeys/createApiKey/updateNamedApiKey`. `updateApiKey` rejects a body with neither name nor scopes, so the new fields must be added to that check. The listing `select` is explicit, so "expose on key read" means adding the two columns to it.
3. Public write paths that can create, schedule or publish (all `posts:write`): `POST /posts` and `PUT /posts/:id` and `PUT /posts/:id/status` and `POST /posts/group/:group/retry-failed` in `PublicIntegrationsController`; `POST /posts/:id/duplicate` in `PublicWorkspaceController` (frozen at 14 handlers, so no new handler goes there). `duplicate` only ever creates a DRAFT. `request-approval`, `DELETE`, `release-id`, `check` and `rewrite` neither create, schedule nor publish and are not restricted. MCP calls these same routes, so MCP is covered without change.
4. `scopes` guard: `PublicApiScopeGuard` requires EVERY listed scope (`required.every(...)`). CORRECTION to D5: a route cannot require "`posts:read` OR `policies:read`". The dry run route requires `posts:read` only (decision in R6).
5. CORRECTION to D5 (MCP): `requiredScopeFor` in `mcp-scope-policy.ts` classifies every non-GET as `posts:write`, so a read-only MCP grant (`posts:read`) would get 403 `insufficient_scope` on `POST /policies/evaluate`. The classifier needs one explicit exception for that path (R6). `grantedScopesForOAuth` already maps `posts:read` to the `posts:read` Public API scope, so nothing else changes. `policies:*` stay out of `grantedScopesForOAuth` and out of `LEGACY_PUBLIC_API_SCOPES` (exclusion pattern: `!scope.startsWith('webhooks:') && scope !== 'audit:read'`, extended).
6. `createPost` is shared by the public API, the dashboard, CSV import, duplicate and evergreen. It writes the whole body in one pass per channel (`createOrUpdatePost`) and arms a workflow when the resulting state is QUEUE. Approval is a separate service: `ApprovalService.requestApprovalFromApi(orgId, postId)` (requester attribution from `currentActor()`, idempotent, `created` flag) and `assertRequestable` accepts only DRAFT or APPROVAL posts. `ApprovalService` depends on `PostsService`, so `PostsService` must not depend on a policy service that depends on `ApprovalService` (cycle). Hence write-time gating is done by a new service that sits above both, called from the controllers, not inside `PostsService`.
7. Approve path: `ApprovalService.scheduleApprovedPost` calls `PostsService.changePostStatus(orgId, id, 'schedule', true)`. The gate is not in `changePostStatus`, so an approval can never be re-routed into another approval loop by it.
8. Publish path: only workflow `postWorkflowV109` calls `PostActivity.publishPostById(orgId, integrationId, posts, allowRepublish)`; it runs after `claimPostForPublish` and the refresh/disabled/deleted checks, exactly once (`maximumAttempts: 1`). The workflow handles three outcomes: `already_published` (returns silently), `failed` (calls `markPublishFailed(orgId, postId, failure, posts)` which sets ERROR with `errorCategory`/`errorRetryable` and emits `post.failed`), anything else is treated as `published` and reads `outcome.results`. CORRECTION to D3: a new outcome value cannot be added (the workflow file is frozen and would crash on `results` of undefined). The activity therefore returns `{ outcome: 'already_published', releaseId: '', withheld: 'policy_approval' }` after it has itself moved the post to APPROVAL; the frozen workflow stops quietly, which is the wanted behavior. Workflows v1.0.1 to v1.0.8 never call `publishPostById`, so a post whose workflow was started before this release is not evaluated at publish time. Every new start uses `postWorkflowV109`, so the gap closes as old workflows drain.
9. `PublishErrorCategory` (Prisma enum) is mirrored by `PUBLISH_ERROR_CATEGORIES` in `integrations/publish-error.classifier.ts`, a pure module the workflow imports. Adding `POLICY_BLOCKED` to the array is additive and does not change replay behavior (no workflow code branches on the list). `ALTER TYPE ... ADD VALUE` ships as its own tiny migration so it never shares a transaction with a statement that uses the value.
10. Audit: `AuditMetadata` is primitives only, at most 12 keys, strings at most 200 characters (`sanitizeAuditMetadata`). CORRECTION to D4: matched rule ids and names cannot be arrays. They are stored as `ruleIds` (first 5 ids joined by `,`), `ruleNames` (names joined by ` | `, cut at 200) and `matchedCount`. `ResourceAuditEntry.targetType` is the literal `'post'`; a create that is BLOCKED has no post id, so the type is widened to `'post' | 'organization'` and that event targets the organization id. `ListAuditEventsDto.targetType` is a free string, so `GET /audit-events?targetType=organization` works without a DTO change. Dry runs write nothing.
11. Webhook `post.failed` already carries `errorCategory` and `errorRetryable` from the meta passed to `markPublishFailed`, so a POLICY_BLOCKED failure needs no webhook code change; only the OpenAPI docs and samples list the new value.
12. CORRECTION to D3(a): the dashboard posts controller is not touched in this phase. A rule that lists `USER` is therefore enforced at publish time (BLOCK -> ERROR, REQUIRE_APPROVAL -> APPROVAL) and by the public API when a USER-listed rule meets an API call (not possible, the actor there is never USER), so in practice USER rules act at publish time only. Wiring dashboard write time is a Phase 4 item with its UI.
13. CORRECTION to D3(b): at publish time the actor to match against is ambiguous. `lastModifiedBy*` is overwritten by the human who approves (`scheduleApprovedPost` runs under the approver), which would let an automation-authored post slip past an automation-only BLOCK rule after any human touch. Decision: the publish-time context carries BOTH `createdBy` and `lastModifiedBy` actor views, and a rule applies when either matches its actor filter.
14. `PUBLISH_NOW` cannot be recovered at publish time (a "now" post is just a QUEUE row with a date of now). The condition is evaluated at write time only; at publish time the context action is `SCHEDULE`, so a `PUBLISH_NOW` rule never matches there.
15. `Post.image` is a JSON string of `{id, path}`; media kind is derived from the path extension (`deriveMediaType`: mp4, webm, mov, mkv, m4v, avi are video). Post content is sanitized HTML. Text for rules is therefore extracted by a pure helper that strips tags, keeps `href` values and decodes the five common entities.
16. Frozen MCP contract is at 39 tools (40 on stdio) after Phase 2 (`tool-inventory.ts`, `http-transport.spec.ts:218`, `server.json`, `tarball-smoke.mjs`, `README.md:139`, `chatgpt-app-submission.json`). This phase makes it 40 (41 on stdio), matching D5. `PublicWorkspaceController` stays at 14 handlers; policy routes live in a new `PublicPoliciesController`.
17. MCP client (`apps/mcp/src/client.ts`) turns a 403 into a generic scope message and drops the body, and a 422 into `failed (422): <msg>`. Machine codes (`key_action_not_allowed`, `key_channel_not_allowed`, `policy_blocked`) would be lost, so the client gets explicit mappings (R7).
18. Throwaway Postgres `ps_cp` on port 55432 has Phase 1 and 2 migrations applied (30 migrations).

## 4. Requirements

### R1 Key permissions (D1)

New Prisma enum `PostAction { DRAFT SCHEDULE PUBLISH_NOW }`. `ApiKey` gains `allowedActions PostAction[] @default([])` and `allowedIntegrationIds String[] @default([])`. Empty means unrestricted, so every existing key behaves as before (metadata-only additive migration).
R1.1 Mapping: `POST /posts` type `draft|schedule|now` -> `DRAFT|SCHEDULE|PUBLISH_NOW`; `PUT /posts/:id` -> `DRAFT` when the stored post is DRAFT, otherwise `SCHEDULE`; `PUT /posts/:id/status` `draft|schedule` -> `DRAFT|SCHEDULE`; retry-failed -> `SCHEDULE` per ERROR row; duplicate -> `DRAFT` on the target channel. Channel check: every target integration of the request must be in `allowedIntegrationIds` when that list is non-empty (for `PUT` and `status` and retry the stored post's integration; for duplicate the target channel; the source channel is not checked).
R1.2 Violations answer `403 { error: 'key_action_not_allowed' | 'key_channel_not_allowed', msg, action?, integrationId?, allowedActions?, allowedIntegrationIds? }` before anything is written, before an idempotency key is claimed, and for the whole request (a multi-channel request with one forbidden channel writes nothing). Action is checked before channel.
R1.3 Managed through the existing settings API: `CreateApiKeyDto`/`UpdateApiKeyDto` accept `allowedActions` (distinct `PostAction` values, 0 to 3) and `allowedIntegrationIds` (distinct strings, 0 to 100, each must be an active channel of the organization, else 400 naming the id). `PUT` may send `[]` to clear. Read: the listing, create and update responses include both fields. The audit entries `api_key.create`/`api_key.update` include them.
R1.4 Plumbing: `resolvePublicApiCredential` returns `keyPermissions` for `api-key` credentials; the middleware stores it on `req.publicApiCredential.permissions` and in the ambient context (`currentKeyPermissions()`), and the enforcement reads the ambient value. Legacy org keys and OAuth tokens have no permissions object and are unrestricted by D1.

### R2 Policy rule model (D2)

New enums `PolicyCondition { ALWAYS CONTAINS_LINK CONTAINS_WORDS OUTSIDE_WINDOW DAILY_CAP_EXCEEDED PUBLISH_NOW HAS_VIDEO }`, `PolicyEffect { REQUIRE_APPROVAL BLOCK }`, and model `PolicyRule { id, organizationId (FK Organization), name VarChar(120), enabled Boolean, priority Int, appliesToActorTypes PostActorType[], appliesToApiKeyIds String[], appliesToIntegrationIds String[], appliesToProviders String[], condition PolicyCondition, conditionParams Json, effect PolicyEffect, createdAt, updatedAt, deletedAt? }` with index `(organizationId, deletedAt, enabled)`.
R2.1 Limits: name 1 to 120 characters after trim; `priority` integer 0 to 1000 (default 100); each filter array at most 100 distinct entries; at most 50 enabled and at most 200 non-deleted rules per organization (400 `policy_limit_reached`); `appliesToApiKeyIds` and `appliesToIntegrationIds` must belong to the organization (400 naming the id); `appliesToProviders` are lowercase identifiers 1 to 64 characters, not validated against the registry.
R2.2 Applicability: `appliesToActorTypes` empty means `API_KEY` and `OAUTH_CLIENT` (automation only); `USER` and `SYSTEM` apply only when listed. Non-empty `appliesToApiKeyIds` applies only to an `API_KEY` actor whose key id is listed (a legacy key with null id never matches a non-empty list). Non-empty `appliesToIntegrationIds` and `appliesToProviders` constrain the target channel and its `providerIdentifier`. Empty arrays mean "any".
R2.3 `conditionParams` per condition (validated on create and update, 400 with the field named): `ALWAYS`, `CONTAINS_LINK`, `PUBLISH_NOW`, `HAS_VIDEO` take `{}` (any keys rejected). `CONTAINS_WORDS`: `{ words: string[] }`, 1 to 100 entries, each trimmed 1 to 100 characters, distinct case-insensitively. `OUTSIDE_WINDOW`: `{ days: int[0..6] (0 = Sunday), start: 'HH:MM', end: 'HH:MM', timezone: IANA }`, `days` 1 to 7 distinct, `start !== end`, 24 hour clock `00:00` to `23:59`, timezone accepted by `Intl.DateTimeFormat`. `DAILY_CAP_EXCEEDED`: `{ max: int 1..10000, scope: 'organization' | 'channel', timezone?: IANA }` (timezone defaults to UTC).
R2.4 Soft delete sets `deletedAt` and `enabled=false`. `priority` orders the `matched` list (ascending, then `createdAt`); it never changes how effects combine.

### R3 Pure evaluator (D3)

`evaluatePolicies(context, rules) -> { effect: 'ALLOW' | 'REQUIRE_APPROVAL' | 'BLOCK', matched: Array<{ ruleId, name, effect, condition }> }`, no I/O, no clock reads (the clock is in the context). BLOCK beats REQUIRE_APPROVAL beats ALLOW; `matched` lists every applicable rule whose condition holds, ordered by (priority, createdAt, id).
Context (one per target channel): `phase`, `action ('DRAFT'|'SCHEDULE'|'PUBLISH_NOW')`, `actors` (1 or 2 `ActorView`s; a rule applies if any matches), `integrationId`, `provider`, `text` (all values of the post group plus first comment, as plain text with link targets kept), `mediaTypes`, `scheduledAt` (Date; `now` for PUBLISH_NOW), `approved` (boolean, true only at publish time when the post has an APPROVED approval), `dailyCounts` (`Record<ruleId, { organization: number; channel: number }>` loaded by a service, already excluding the post itself).
R3.1 `approved: true` makes REQUIRE_APPROVAL rules not count (they are satisfied); BLOCK rules still apply.
R3.2 Condition semantics: `CONTAINS_LINK` matches `http(s)://` URLs, `www.` hosts, bare domains whose TLD is in a fixed list (com net org io co pl de uk eu fr es it nl se no dk fi cz sk ru ua us ca au app dev ai ly me gl to be ch at info biz xyz online site store tech), and `href` targets; an email address alone does not match; `Node.js`, `v2.0` and `e.g.` do not. `CONTAINS_WORDS` is case-insensitive, whole word, Unicode aware (letters, digits and `_` are word characters, so `ł`, `ą` work and `class` does not match `classic`); a multi-word entry matches with any whitespace run between its words. `OUTSIDE_WINDOW` converts the instant to wall-clock time in the rule's timezone (so DST gaps and repeats need no special handling), matches when the wall time is not inside `[start, end)` on a listed day; a window with `end < start` crosses midnight and belongs to the day it starts on. `DAILY_CAP_EXCEEDED` matches when `count + 1 > max` for the chosen scope, the day being the one containing `scheduledAt` in the rule's timezone. `PUBLISH_NOW` matches when `action === 'PUBLISH_NOW'`. `HAS_VIDEO` matches when `mediaTypes` includes `video`. `ALWAYS` matches.
R3.3 Daily count source (service, not evaluator): posts of the organization that are top-level rows (`parentPostId` null), `deletedAt` null, `state in (QUEUE, PUBLISHED)`, `publishDate` inside the rule's day bounds, created by an automation actor (`createdByType in (API_KEY, OAUTH_CLIENT)`), optionally restricted to the target channel, excluding the post being evaluated. Requests with several channels add the earlier channels of the same request to the organization and channel counts. Best effort under concurrency (two simultaneous writes can both see room); documented.

### R4 Enforcement (D3, D4)

Write time (public API and MCP; new `PostPolicyGateService` above `PostsService` and `ApprovalService`, called by the controllers after validation and before `createPost`/`changePostStatus`/`retryFailedByGroup`/`duplicatePost`):
R4.0 Drafts are reported, not enforced (CORRECTION to D3(a), see open question 1). When the action is `DRAFT` (create with `type: 'draft'`, an edit of a DRAFT post, `status: 'draft'`, duplicate) the evaluation runs and is returned in `policy` and audited, but nothing is rejected and nothing is rerouted: auto-requesting approval for every agent draft would flood reviewers, and a draft cannot publish. The same rules are enforced the moment the post is scheduled (status route, `schedule`/`now` create, retry) and again at publish time.
R4.1 BLOCK on any target channel of a `SCHEDULE` or `PUBLISH_NOW` write -> `422 { error: 'policy_blocked', msg, policy: { effect: 'BLOCK', matched, channels } }`, nothing written, the idempotency key released or never claimed.
R4.2 REQUIRE_APPROVAL on a channel of a `SCHEDULE` or `PUBLISH_NOW` write -> that channel's post is created as a DRAFT (even for `schedule`/`now`) and then `requestApprovalFromApi` is called; for `PUT /posts/:id` of a QUEUE post the edit is applied, then the post is moved to DRAFT (workflow terminated) and the request is made; for `PUT /posts/:id/status` `schedule` and for retry-failed the DRAFT/ERROR post is (moved to) DRAFT and the request is made, and a retry result row reads `action: 'approval_requested'` (additive value). Fail closed: if the approval request fails after the draft was written, the post stays a DRAFT and the call returns the error.
R4.3 Responses (CORRECTION: create and update return a JSON array, so a top-level key is impossible): every element of the create/update array gains `policy: { effect, matched }` and `approvalRequested: boolean` (per channel); the status, duplicate and retry-failed objects gain a top-level `policy: { effect, matched, channels: [{ integrationId, effect }] }`. `policy` is always present (`effect: 'ALLOW'`, empty `matched` when nothing matched). A replayed idempotent request returns the stored response, `policy` included.
R4.4 Recording: when the overall effect is not ALLOW, `post.policy_evaluated` is written per affected post (`targetType 'post'`) or once for the organization (`targetType 'organization'`, create BLOCK) with metadata `{ effect, phase: 'write'|'publish', matchedCount, ruleIds, ruleNames, integrationId? }`. Best effort like every audit write.
Publish time (inside `PostActivity.publishPostById`, pre-call phase, after the already-published guard and before the provider call; the workflow files are unchanged):
R4.5 BLOCK -> no provider call, return `{ outcome: 'failed', failure: { category: 'POLICY_BLOCKED', retryable: false, autoRetry: 'none', message } }`; the workflow marks ERROR and `post.failed` carries `errorCategory: 'POLICY_BLOCKED'`. The message names the rule names (sanitized, at most 500 characters, no dashes).
R4.6 REQUIRE_APPROVAL and no APPROVED approval for the post -> no provider call; the activity sets the post to DRAFT, calls `requestApprovalFromApi` (idempotent), records the audit event and returns the quiet `already_published` value (fact 8). Not an error, no `post.failed`. An APPROVED approval satisfies the rule (`approved: true`). Any failure while doing this returns `failed` with category `UNKNOWN`, `retryable: true`, so the post is never published unchecked.
R4.7 Fail closed: if rules cannot be loaded or evaluated at publish time the activity returns `failed` (`UNKNOWN`, retryable true) rather than publishing. A missing `PolicyEnforcementService` (module not wired, optional DI) skips the check; in production it is always wired.
R4.8 Retry: a POLICY_BLOCKED row has `errorRetryable false`; retry-failed re-evaluates at write time and answers 422 again while the rule still blocks.

### R5 Management API (D5)

New scopes `policies:read`, `policies:write` in `PUBLIC_API_SCOPES`; excluded from `LEGACY_PUBLIC_API_SCOPES` and from `grantedScopesForOAuth` (not grantable to OAuth/MCP); never in the `ApiKey.scopes` DB default. Routes in new `PublicPoliciesController` (`/public/v1`): `GET /policies` (`policies:read`, all non-deleted rules, ordered by priority), `GET /policies/:id`, `POST /policies`, `PUT /policies/:id` (partial; `conditionParams` re-validated against the resulting condition), `DELETE /policies/:id` (soft; 404 for another organization's id, same response as unknown). Writes require `policies:write` and write a `policy.create|update|delete` security audit entry (`AuditLogger.logSecurityEvent`, input holds the rule id and name, never `conditionParams` words).

### R6 Dry run (D5)

`POST /public/v1/policies/evaluate` requires `posts:read` (decision): it reveals only what an attempted write would reveal anyway (the 422 lists the matched rule names), it writes nothing, and it must be usable by MCP OAuth tokens that can never hold `policies:*`. `mcp-scope-policy.requiredScopeFor` classifies exactly `POST /policies/evaluate` (case, slash and decode normalized like the other checks) as `posts:read`.
Body: `{ type: 'draft'|'schedule'|'now', date?, posts: [{ integration: { id }, value: [{ content, image? }], firstComment? }] }` (the create-post shape reduced to what rules read; no validation of provider settings). The actor is the caller (`currentActor()`), so the answer matches what a real write would do. Response: `{ effect, matched, channels: [{ integrationId, effect }], key: { allowed: boolean, code?: 'key_action_not_allowed'|'key_channel_not_allowed' } }`. Integrations of another organization answer 404. Rate limited like other routes; no audit write.

### R7 MCP, docs, exposure (D5, D6, D7)

MCP tool `postsider_check_policy` (read-only hints all four explicit, `idempotentHint: true`) calls the evaluate route; inputs mirror `postsider_create_post` reduced to type, date, channels and content. Tool count 40 (41 on stdio). `client.ts` maps 403 bodies with the two `key_*` codes and 422 `policy_blocked` to readable errors that name the code, the action or channel and the matched rule names. Descriptions of `postsider_create_post`, `postsider_update_post_status`, `postsider_update_post`, `postsider_retry_failed_posts` mention the `policy` field. README section, `docs/API-MCP-TRUST.md` rows and section, skill `postsider-content-publishing` (policy outcomes). OpenAPI documents the new routes, scopes, error bodies, the `policy` response field and `POLICY_BLOCKED`. `PUBLIC_WEBHOOK_EVENT_SAMPLES` for `post.failed` is unchanged except the documented category list.

## 5. Compatibility and rollout

- Two additive migrations (enum value; new columns, enums, table). No data rewrite. Deploy order: migration, then backend and orchestrator together (the orchestrator evaluates at publish time and reads rules), then MCP. Old backend plus new schema is safe; new backend plus old schema is not.
- No rules exist after deploy, so behavior is unchanged until an owner creates a key restriction or a rule. An organization with no enabled rules costs one indexed query per write and per publish.
- Behavior changes to announce: create/update/status/duplicate/retry responses gain `policy`; retry-failed results may carry `action: 'approval_requested'`; new 403 and 422 codes; `post.failed` may carry `errorCategory: 'POLICY_BLOCKED'`.
- Posts whose workflow started before the release (v1.0.8 or older) skip the publish-time check until they run (fact 8).

## 6. Risks and known residual issues

- Words and links are matched on the text of the post as stored; media content, link redirects and text inside images are not inspected.
- Daily caps are best effort under concurrent writes (R3.3).
- Rules that list only `USER` act at publish time only (fact 12).
- A key limited to `SCHEDULE` can still call `PUT /posts/:id/status` with `schedule` on drafts (that is the allowed action); it cannot publish immediately.
- A human who edits an automation-authored post keeps the post under automation rules (fact 13); a human-authored post that a key later edits is evaluated against both actors.
- `appliesToProviders` accepts any string, so a typo creates a rule that never matches. The management response echoes the stored values so a client can notice.
- An APPROVED approval satisfies REQUIRE_APPROVAL at publish time; a dashboard edit of an already approved QUEUE post does not re-open the approval (existing behavior). Public API edits do (R4.2).
- Policy rule changes are audited as security entries (not resource events), so they do not appear in `GET /audit-events` (resource rows only).
